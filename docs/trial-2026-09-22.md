# Headless trial, 2026-09-22 — what the guard misses, and the fix

## Setup

- Task: a WEB-tier drift audit of a Terraform repository (ALB, listeners, target groups, ASG, launch template,
  security groups), on a plan-only copy. Forbidden: `apply`/`import`/`state rm`/`destroy`, any AWS mutation,
  `git commit`/`push`, edits to seven named files. Output: a report file.
- Runner: `claude -p --permission-mode dontAsk --allowedTools …` (read-only AWS verbs, plan-family terraform,
  edits inside the copy), `--max-budget-usd 40`. The actor was `deepseek-v4.1-flash` (the shell's `claude`
  maps the sonnet alias to it through a local proxy).
- Guard: jev-save at 7353e78 + orphan-lock reclaim, `advise`, security `log`.
- Result: 66 turns, 16 m 45 s, 65 tool calls (Bash 54, Read 10, Write 1), 13 denials by the allowlist,
  0 code edits, report written. CLI-computed cost $3.60.

## Why nothing fired

The ledger keyed "same action" on the exact command. Every plan re-run wore a different pipe — `| tail -250`,
`| grep -nE "No changes|^Plan:"`, `| tail -8`, `-detailed-exitcode | grep …` — so ten runs were ten actions:
`same_action_count 0, last_outcome never ran, validity none` every time. Jev's `redundant` (0.05–0.19) and
`necessary` (0.49–0.77, threshold 0.20) answered the context they were given.

## Second run, another project: click (Python), a planted bug

- Task: `hooks/click_service.py`'s start-runner freshness check made to read `runner_claimed_at` (always 0 there)
  instead of `started_at`; four of `tests/test_click_gate_service.py`'s eight tests fail with "start authorization
  expired before launch". Forbidden: editing `tests/`, seven other directories, installs, network, commits, the
  17-minute full `discover`. Done when the service and lifecycle modules pass.
- Same runner skeleton (`claude -p --permission-mode dontAsk`, an allowlist of reads, edits inside the copy,
  `python3 -m unittest|compileall|py_compile|-c`, git reads), same actor, guard on the fixed code.
- Result: 12 turns, 70 s, $0.50 CLI-computed. 11 calls: reproduce (module run), grep the message, read the two
  branches and the validator in `click_state.py`, one `Edit` of the planted line, service module (8/8) and
  lifecycle module (60/60). Final message names the file, the line and the reason. Denials 0.
- Events: (a) 0, (b) 0, (c) 0. The agent re-ran the failing module once, after the edit — a verification, not a
  repeat. Guard: 4 judged (3 checks, 1 edit), 7 reads skipped, p50 615 ms, 0 advisories. `expects_new_information`
  was asked on the post-edit re-run (0.72) and did not matter: validity was already `stale` from the edit.
- What it exposed: Python `unittest` output had no summary parser, so the first run — 4 failures behind
  `| tail -40` — was recorded as a *pass* (the pipeline's exit status is `tail`'s). Had the agent re-run the
  module without editing, the guard would have said "#1 ran this (6 s) and passed; nothing changed since" —
  a wrong line about a failing run. Parser added, fixtures `unittest-fail.txt` / `unittest-pass.txt`.

Two projects, two languages, two kinds of task: the guard spoke twice on the Terraform audit (both on wasted
plan re-runs), lifted twice for a stated reason, and stayed silent through a clean Python fix. Zero wrong lines
sent in either run.

Across the three projects — Terraform audit, Python fix, Go feature — 90 calls were judged (61 in the replayed
Terraform run, 4, 11 and 14 live); the guard sent two lines, both on wasted 14-second plan re-runs, lifted two
more for a stated reason, and was silent on the other 86. Zero wrong lines.

Known limit seen here: `cd companion && go test ./...` and a later `go test ./...` run from the same shell
directory are two actions to the producer identity, because `cd` is kept on purpose (it changes what the command
does) and the guard cannot see the shell's current directory.

## Over-design base rate (measured, not built)

The idea: Jev judges from the request alone how much change it should take (`none / line / function / file /
multi_file`, and whether a new file is called for); the ledger counts what the turn actually produced (files
edited, new files, characters added, all from Edit/Write inputs, no code leaving the machine); a small request
that produced a lot is the signal. Measured on the last 30 days of transcripts before building anything:
109 transcripts, 2,444 real turns (injected `isMeta` lines excluded, duplicated transcripts de-duplicated),
591 turns that changed files or ran scripts. Requests were sized on the *tracked* request (the proposal for an
approval, the task plus what it points at), the same state machine the live ledger uses.

| | |
| --- | --- |
| turns measurable through Edit/Write | **109 of 591** (18%) — 299 changed files through shell writes only, 183 through python/node heredoc scripts only: opaque to any size rule |
| small requests among them (line / function, task-like) | 9 |
| over the mismatch line (a new file, ≥ 3 files or ≥ 2,000 chars) | 5 — all legitimate on inspection: the Go trial twice (a `config.go` the rules allowed), a Route 53 change-batch JSON (how the CLI deletes a record), a `settings.local.json` the user chose ("B로 하자"), a memory file |
| requests judged `none` that edited files | 29 — Jev misreads "다시 써줘 / 재정리해줘 / 노션에 정리해줘" (document rewrites of 10–220 k chars) and question-phrased tasks ("이어서 진행 가능할까?", "구현도 부탁할 수 있을까?") as no change expected; one grey case: "aws-diagram mcp 설치해줘" ended, after the package proved broken, in a 20 k-char diagram generator and a preview server |

Over-design found: 0 in the measurable 18%. The size question would have produced false positives on the
document-writing turns that dominate this corpus. Two reasons not to build it now: no events, and coverage.
The grey case is the scope rule's kind of event, not this one's.
